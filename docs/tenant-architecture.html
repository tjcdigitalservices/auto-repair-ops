How this SaaS is structured

One app codebase. Many auto-repair shops (tenants). Each shop can have multiple branches. Middleware only answers one question: “Which shop is this request for?”

1. The ownership hierarchy

Platform (you / Cursor ops) Super admin at /platform — creates tenants, suspends subscriptions
owns many ↓
Tenant A — “Acme Auto” slug: acme · one subscription · its own branding & catalog
Tenant B — “Legacy Shop” slug: legacy · bootstrap tenant on a fresh DB
each tenant owns ↓
Main Branch default location · public website uses this branch’s settings
North Branch another location · same shop, separate stock / customers / JOs
each branch has ↓
Staff owner / admin / mechanic… — always tied to a tenant + usually a branch
Key idea: “Owner” means tenant owner (all branches in their shop) — not platform owner. Platform people are in platform_admins, separate from shop staff.

2. What middleware does (and doesn’t)

1
Request arrives

Browser hits a URL on your Next.js app.

2
Resolve tenant slug

Path, subdomain, query, cookie, or default legacy.

3
Stamp the request

Sets header x-tenant-slug (+ cookie). Does not query the DB.

4
Page loads data

Server code uses that slug to load branding, branch, catalog for that shop.

Middleware is a labeler — not login, not business rules, not billing.

3. Localhost vs production (same code)

Localhost No real subdomain

Most of the time you just open:

http://localhost:3000

Middleware has no subdomain, so it uses:

  • Cookie if set, else
  • NEXT_PUBLIC_DEFAULT_TENANT_SLUG, else
  • legacy

To open a specific shop without DNS:

http://localhost:3000/t/acme
http://localhost:3000/?tenant=acme

Production Subdomains (optional)

When you set NEXT_PUBLIC_ROOT_DOMAIN=example.com:

https://acme.example.com

Middleware reads subdomain acme as the tenant slug.

Path style still works too:

https://app.example.com/t/acme

Wildcard DNS + TLS are ops setup (documented in white-label docs) — not needed for local dev.

4. Two different “who am I?” questions

  • Public website — “Which shop’s marketing site is this?” → answered by middleware slug (legacy /acme / subdomain)
  • Logged-in ops app — “Which staff user is this?” → answered by Auth + staff.tenant_id / platform_admins

So on localhost, visiting /login as a staff user from Acme still scopes their dashboard to Acme’s data via the database — even if the public site cookie says legacy.
